# ADR-0013: 任务执行技能 run-tasks（串行前沿 + 三层授权闸门）

## 日期

2026-08-09

## 状态

已接受

## 背景

`/grill-me` → `/to-spec` → `/to-tickets` 产出一组带 `Blocked by` 依赖的子议题后，缺一个执行编排器：把「读议题 → 按依赖序实现 → 验证 → 合入/关闭 → 跑不完的交接」跑起来。目标是**无人值守吞吐**——用户走开时尽量多完成任务。

关键约束：

- 合入 main、关闭议题是**不可逆高危动作**，无人值守下没有人类兜底。
- 执行可能被中断/跨会话，任务状态必须**仅凭 GitHub 就能重建**，否则无法恢复。
- 权限系统会拦截 `git merge`/`gh issue close` 等命令——**会话里授权 ≠ 权限系统放行**。

## 决策

引入本地技能 `run-tasks`（`~/.claude/skills/run-tasks/`），user-invoked（`disable-model-invocation: true`），按下列原则编排。

### 串行前沿执行

一次只派一个实现子代理（**严格串行**）。每个任务从上一任务合并后的 main 起分支，基线平凡、无冲突；共享代码库上并行 worktree 的合并冲突是主要反面。多个兄弟任务同时解锁时，按议题体内 `# NN —` 序数取最前者（to-tickets 本就按依赖序编号），保证跨运行可预测。

### GitHub 为状态事实源

每个子议题任一时刻处于六态之一，仅凭 GitHub 可重建：**未开始 / 进行中 / 等待决策 / 可续作 / 完成 / 卡住**。等待决策用 `ready-for-human` 标签 + `🚦` 评论首行标记；卡住用 `🚫` 评论。人类在 `🚦` 之后追加评论 → 转为可续作。中断、重跑、跨会话都不丢东西。

### 三层授权闸门（禁止模糊确认）

1. **值守模式**：启动先问用户会不会走开。**无人值守只在用户明说会走开时启用**；否则值守模式，每任务合并/关闭前停下等授权。
2. **合入/关闭授权**：要用户**逐字明确**说出授权语句，如「满足测试要求的前提下，授权合并、关闭议题」。只有绑定条件（测试满足）+ 明确动作（授权合并/关闭议题）的完整语句才算授权；`y`/`同意`/`确认` 等模糊词不算。拿不准 = 未授权。
3. **权限边界**：高危命令会经过权限系统。未授权被拦是预期安全网；已授权的无人值守合入需预先 allowlist，否则停在权限提示处，任务进 `待合入`。

### 子代理四结局 + 重启复用

子代理结局：**完成**（无人值守已授权 → 合入+关闭+评论）/ **待合入**（值守/未授权 → 只推分支留评论）/ **提问**（`🚦` 评论 + 带问题原文返回；值守等答复、无人值守继续跑）/ **卡住**（`🚫`）。人类决策落地后**重启**该子任务：有分支/worktree 则复用（落后 main 先 rebase），否则新建。

### 终局处理

前沿空时：子议题全关闭 → 关父议题 + 逐条汇总评论；否则父议题保持开 + 交接评论（`#n — 状态 — 问题/分支在哪 — 下一步`，等待决策/待合入/卡住分开列）。

## 理由与权衡

- **串行 vs 并行**：并行的吞吐诱惑不值当——同 epic 的 to-tickets 垂直切片高度耦合（本次 #29–#39 全在动 pom/包结构），后合的必然与先合的冲突。串行把分支基线变成平凡解。
- **user-invoked vs model-invoked**：合并到 main 的高危编排器不该被代理自主触发；且与流水线其余技能（grill-me/to-spec/to-tickets）一致，零 context load。代价是认知负荷：用户须记得 `/run-tasks` 存在。
- **GitHub 为事实源 vs 本地状态文件**：GitHub 议题/评论/标签/分支本身就是记录，无需额外状态文件，天然支持跨会话恢复。
- **三层闸门**：把「用户走开才无人值守」「明确授权语句」「权限系统放行」三件互相独立的事分开设防，缺一不可。
- **干跑（--plan）**：只读不派，合跑前审查与安全评估的手段。

## 不做什么（Out of Scope）

- 并行前沿执行（见理由）；每任务合并前重复询问（会杀死无人值守）；轮询议题评论区等人类答复（只响应，不主动追）。
