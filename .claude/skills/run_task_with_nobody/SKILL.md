# Run Task With Nobody

无人值守执行一批带依赖的 GitHub 议题（主议题 + 子议题）。primary 保持**薄**：建 work 分支、算前沿、派一个子代理、收薄回报、判成功/跳过、写交接。子代理**全权自治**：编码、自审、测试、提交、推送全部在自己的对话里完成，最终只回一份成果摘要。合入 main 是唯一留给人类的高危动作。

上游 `/grill-me` → `/to-spec` → `/to-tickets`。**前沿** = 所有阻塞者已关闭的议题；**交接** = 留给下一个代理/人类的路标。底线：**状态以 GitHub 为准**——中断、重跑、跨会话都不丢东西。设计权衡见 `docs/adr/0014-run-task-with-nobody.md`。

## 触发与授权

只由用户手动触发。实际开跑的触发语句必须**逐字包含**：

> 无人值守，授权执行。

这一句同时声明「用户会走开」与「本批无人值守执行已获授权」两项前提。本技能**全程无合并操作**——合入 main 由用户自己执行。缺一字即拒绝开跑（干跑 `--plan` 除外，只读无需授权）。**合入 main 不由本技能执行**——技能只产出 work 分支，合 main 是用户回来后的唯一动作。拿不准 = 未授权。

## 前置要求

- `git push` 已 allowlist。无人值守下未放行的命令会停在权限提示等一个不存在的人。
- `gh issue *` 可写评论（通常已 allowlist）。
- 技能不执行 `git merge`、不关闭议题——合入 main 与关闭议题由用户自己执行。

## 干跑（--plan）

传 `--plan` 或"只看顺序"时不派任何子代理：读输入、建依赖图、算前沿，打印执行顺序 + 每个任务的状态分类（按状态模型），然后停。这是合跑前审查与安全评估的手段。

## 状态模型（以 GitHub 为准）

每个子议题任一时刻处于恰好一种状态，仅凭 GitHub 可重建：

| 状态 | 可观测特征 | 处理 |
|---|---|---|
| 未开始 | 开着，work 分支无 `#N` 提交，无 🚦/🚫 评论 | 可派发 |
| 完成 | 「已并入 `work/…` @`sha`」评论 + work 分支含 `#N` 提交 | 跳过 |
| 等决策 | `ready-for-human` + `🚦` 评论（问题 + 暂存分支名 + sha） | 等人类答复后重启 |
| 卡死 | `🚫` 评论（原因 + 暂存分支名 + sha） | 跳过 |
| 进行中 | work 分支含 `#N` 提交，无完成/🚦/🚫 评论（上次中断） | 核对补记或重做 |

`🚦`/`🚫` 是评论首行的原样标记，grep 即可分类。

## 执行循环

1. **建 work 分支**（完成标志：`work/<父议题>-<NN>` 已从 main 建出并 push 到远端）。后续所有提交落在此分支。
2. **建依赖图**：解析每个子议题的 `Blocked by: #N` 边。
3. **算前沿**：未开始 + 阻塞者全关。多个兄弟同时解锁时按议题体 `# NN` 序数取最前者（无则按议题号）。
4. **取一个任务**：严格串行，同一时刻至多一个实现子代理。
5. **派子代理**（Agent 工具，命名 `run-task-<N>`，简报见下）。完成标志：子代理已返回薄报告。
6. **处理回报**（完成标志：任务已归类为成功或跳过）：
   - **成功** → 重算前沿，回 3。
   - **跳过** → 走「跳过」节，回 3。
7. **终局**（完成标志：交接评论已发、父议题保持开）：前沿空——可跑任务全做完、只剩被跳过任务卡住的依赖者——按「终局处理」。

## 保绿不变量

work 分支**永远绿，每次 push 都是绿的**。子代理无法保绿时不推送——把失败工作提交到本地（带 `#N` 前缀）但不 push，返回失败原因。

## 两种回报

子代理结局对 primary 只有两种：

- **成功**：绿、push、work 分支出现 `#N` 提交、议题发「已并入 `work/…` @`sha`」评论、返回成果摘要（变更列表 + 测试结果 + 提交 sha）。
- **跳过**（🚦 需决策 与 无法推进都算）：
  - **🚦 需决策**：不重试。若工作已绿则直接 push + 发 `🚦` 评论（问题原文）；若不绿则按「跳过」节暂存回滚 + 发 `🚦` 评论（问题 + 暂存分支名 + sha）。等人类答复后重启。
  - **无法推进**（测试过不了 / 卡住）：**最多重试一次**——换新子代理、简报附上次失败原因；仍失败才跳过。跳过同上：绿则 push + `🚫` 评论（原因），不绿则暂存回滚 + `🚫` 评论（原因 + 暂存分支名 + sha）。

## 跳过

跳过 = 本地暂存 + work 分支回滚 + 继续下一个不依赖它的任务：

1. 基于失败提交建本地暂存分支 `wip/issue-N`（`git branch wip/issue-N <失败提交>`）。
2. work 分支回滚到上一绿点（`git reset --hard <基线sha>`，即子代理开始时的分支 tip）。
3. 远端 work 分支本就绿（失败工作没 push 过），无需再推。
4. 暂存分支只存本地，不推远端；🚦/🚫 评论里记死：**失败原因 + 暂存分支名 + sha**——跨机器丢了也能凭交接重做。

## 派发简报

把议题全文 + 评论、当前状态、验证契约原样交给子代理：

```
实现本仓库的 GitHub issue #<N>。仓库约定见 AGENTS.md。

议题正文与验收标准：
<全文>

当前状态：<未开始 | 等决策（附人类答复）>
基线：work/<父议题>-<NN> 当前 tip（记录该 sha）。直接在其上工作，不建新分支、不改其他分支。

做：
1. 直接在基线上工作；每次提交首行以 `#<N>:` 前缀开头。
2. 按仓库实现约定实现：可行的接缝处用 tdd、常跑类型检查。
3. 验证按仓库测试指南：逐一核对每条 @requires-* 声明，缺必需环境就是【无法推进】。
4. 全量测试绿 → push → 在议题发「已并入 work/… @sha」评论 → 返回成果摘要（变更列表 + 测试 + 提交 sha）。
5. 结局：
   - 需要业务决策 → 若工作已绿：push + 发 🚦 评论（问题原文）；若不绿：提交但不 push，返回基线 sha 与问题原文。
   - 任务不可能或环境阻塞 → 同上：绿则 push + 🚫 评论（原因）；不绿则提交不 push，返回原因。
   - 无法保绿 → 提交但不 push，返回失败原因与基线 sha。
6. 只动自己的议题；父议题保持开。
```

## 重启（人类决策落地后）

用户在对话中答复 `🚦` 问题，或技能重跑发现**等决策**任务已有人类评论时，重启该子任务：

- **复用暂存分支**：从 `wip/issue-N` 取回工作，rebase 到当前 work 分支 tip，继续加 `#N` 提交。
- 无暂存分支（工作本已绿）则直接在当前 tip 继续。
- 派新子代理，简报同上，另附**人类的决策**，让它继续而非再问一遍。

## 终局处理

前沿空时，在父议题发交接评论：

- work 分支名 + 合入指令：`gh pr create work/<名> --base main`。
- 完成项一行一条；跳过项按 **等决策 / 卡死** 分开列（各带暂存分支名 + sha）；被跳过项连带阻塞的未开始项单列。
- 父议题保持开。合入 main 与关闭议题由用户执行。

## 安全规则

- 合入 main、关闭议题：仅用户自己执行，技能不碰。
- 推送只发生在 work 分支（绿时）与暂存分支（本地）；不 force-push。
- work 分支永远绿——任何不绿的状态都不推送。
